## Evinced remediation guidance

**Cause:**  
The element fails to expose correct interactivity semantics due to one or more of the following reasons:

- **Use of non-semantic HTML elements** such as `<div>` or `<span>` for interactive behavior, often combined with click handlers but without the necessary programmatic semantics.
- **Missing or incorrect ARIA roles** on custom interactive components, leading assistive technologies to misinterpret the element's purpose.
- **Mismatch between visual appearance and programmatic meaning**, where the element looks interactive but lacks the semantic information required by assistive technologies.

These conditions result in assistive technologies not receiving the data needed to classify or announce the element correctly.

---

**Effect:**  
When semantics are missing or incorrect, users of assistive technologies encounter significant barriers:

- **Screen readers may ignore the element** entirely or treat it as non-interactive text.
- **The element's purpose, behavior, and expected outcome** are not announced, preventing users from understanding how to interact with it.
- **Navigation efficiency is reduced**, as users lose reliance on semantic shortcuts (e.g., navigating by buttons or links).
- **Voice-control users are impacted**, since voice-based systems depend heavily on accurate semantics to trigger elements by name.

This creates uncertainty, reduces predictability, and can prevent users from completing tasks.

---

**Technical Context:**  
Understanding semantic roles is crucial because:

- **Native HTML elements define a "semantic contract".** They inherently provide meaning, keyboard behavior, and state announcements (e.g., pressed, expanded, selected).
- **Assistive technologies rely on this semantic contract**, interpreting either the built-in semantics or the explicit ARIA roles to determine:
  - How the element behaves  
  - What interaction model it follows  
  - Which states it exposes  
- **Generic elements do not provide these semantics**, requiring developers to replicate:
  - Keyboard interaction support (Enter/Space)
  - Focus management
  - State transitions and announcements
- **Incorrect or contradictory roles** break the expected behavior model, leading to misinterpretation by assistive technologies.

Because native elements already provide all of this reliably, recreating these behaviors manually is error-prone and frequently incomplete.

---

**Suggested Solutions:**  
Follow these mutually exclusive steps in strict order:

1. **Add or correct ARIA roles on non-semantic or incomplete elements**  
   - Apply an ARIA role that reflects the intended interactivity, such as `role="button"`, `role="link"`, `role="checkbox"`, or others.  
   - Ensure the interaction model (keyboard support, focusability, state exposure) is implemented to match the assigned role.  
   - Provide required ARIA attributes when applicable (`aria-pressed`, `aria-expanded`, etc.).  
   This step is used whenever the element is non-semantic or lacks complete semantics.

2. **If the element is already using an incorrect native semantic or interactive tag, change it to the correct one**  
   - Only apply this step when the element *has* a native tag, but that tag does not match its intended function.  
   - Examples:  
     - A `<span>` used as a button → replace with `<button>`  
     - A `<div>` used for navigation → replace with `<a href="…">`  
   This step is only chosen when Step 1 is not applicable based on the element's current semantic type.

3. **If neither of the above steps is applicable, convert the element to the correct semantic structure**  
   - Restructure or rebuild the element using the appropriate semantic pattern when neither ARIA nor tag correction can represent the intended interaction.  
   - Example: converting a custom tree, menu item, or composite widget into the correct semantic/ARIA pattern.

This ordered procedure ensures compliance with the required mutually exclusive decision flow and guarantees accurate semantics exposure to assistive technologies.
